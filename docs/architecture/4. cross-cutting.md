# Cross-cutting concerns

Part of the [Sprout architecture docs](README.md). See the [overview](1.%20overview.md) for the architecture and data model these concerns apply to, and [decisions](6.%20decisions.md) / [risks](5.%20risks.md) for the accompanying decision log and risk register.

## 1. Sourcing and provenance
- `Sourced[T]` rejects a non-null value with no `source_url`. `value=None` means "not disclosed" and must render as such, never zero or blank.
- Per-fact `retrieved_at` (UTC) supports a staleness policy; registry facts can lag up to 7 days via the HTTP cache.
- Multiple sources per field can coexist. The Phase 6 verifier records its verdict as a `verification:<claim>` fact sourced to the second URL and adjusts only the claim's confidence and note, never its value (D40).
- Not provenance-bearing: `category`, `news_item` (source is the feed), free-text fields.
- The winning-value rule (A6), for which value wins when a field has several facts: a valued fact beats a NULL one, then the most recent `retrieved_at`, then the higher `confidence`; confidence is not first, because a stale high-confidence fact would otherwise beat a fresher medium one after a re-run. Implemented as `db.winning_facts`; read by the classify and news prompts, the verifier's `claim_row`, `status.profile_gaps`, the evals and the stage/business-status helpers in `app/queries.py`, not yet by a full profile read for the dashboard (see the [Phase 3 page](phases/phase-3-enrichment.md#the-winning-value-rule-a6)). "Sources disagree" is surfaced only between facts from the same refresh, since an older fact from a superseded run is stale, not a disagreement.
- Funding rounds are tracked in a dedicated `funding_round` table, one row per round, each sourced independently; `save_profile` replaces a company's rounds on every save, so there is no history across runs, only within the latest one.
- SQLite treats NULLs as distinct in UNIQUE constraints; `save_fact` dedupes in application code rather than relying on the constraint.

## 2. Agent orchestration
- A deterministic supervisor (D27) selects companies and runs them on a worker pool: `asyncio` with `to_thread`, one resource bundle per worker, concurrency default 4 (D38). Details, interfaces and the CLI are on the [Phase 6 page](phases/phase-6-multi-agent.md).
- Per company, sequentially in one worker: enrich, classify (bulk model), news (bulk model), verify (strong model, only for a funding or stage claim). A step that is fresh is skipped and a failed step does not stop the later ones, except that nothing runs without an ok enrich. Parallelism is across companies.
- Models: bulk `claude-haiku-5-5` for extraction/classification/news; strong `claude-sonnet-5-5` for verification/synthesis; overridable via `SPROUT_BULK_MODEL` / `SPROUT_STRONG_MODEL`. An unpriced override fails closed in `costs.py`. Per-agent caps are in [section 9](#9-phase-6-agent-caps-and-run-budget).
- The enrichment loop (see the [Phase 3 page](phases/phase-3-enrichment.md)) uses `tool_choice: auto`, explicit effort, a prompt-cached conversation, and handles `pause_turn`/`server_tool_use`, under per-run caps on iterations, USD and searches. There is no per-run fetch cap. `BatchBudget` (Phase 5) caps spend across many runs: `run_evals` always uses it, `sprout.enrich --max-total-usd` opts in (default no cap), and the Phase 6 orchestrator always uses it as the single cap over every agent's spend (a lock makes it safe for worker threads). A failed run persists only its `run_log` row; the orchestrator's retry policy (D39) re-runs it.
- Resume: the unit of work is a company step; one `run_log` row per agent run, committed first and completed in one final transaction. Per-company status is derived from `run_log` (latest attempt, `failure_category`, newest ok `finished_at`; see the [data model](2.%20data-model.md#per-company-status-derived-not-stored)), not stored: a fresh ok step is skipped and a failed latest attempt is retried up to 3 times across runs.
- A company failure is recorded on its `run_log` rows (`failure_category`) and the run continues. Target at least 85% of the working set `ok`.

## 3. Error handling

| Boundary | Failure | Behaviour |
|---|---|---|
| Companies House / RSS | 429 or 5xx | Retry with backoff and `Retry-After`, then `FetchError` |
| Companies House | 404 | Cached, treated as no result |
| RSS | One feed broken | Reported in `failed_feeds`, exit 1, others continue |
| Web fetch | robots, private IP, content type, URL policy violation | `FetchBlockedError`, returned to the model as a tool error |
| Web fetch | robots.txt unreachable | Refuse |
| Web fetch | Response slower than `max_seconds` (30 s total, Phase 5) | `FetchError`, not retried |
| Web fetch | Page larger than the tool-result cap | Truncated to 8,000 characters (`TOOL_RESULT_MAX_CHARS`) with a "[truncated]" marker; `WebFetcher` caps at 20,000 characters |
| Companies House tool | 404 or invalid number | Returned to the model as a "no such company" error string; not retried |
| Server-side search | `max_uses_exceeded`, `unavailable`, rate limit | Arrives as an error result block, not an exception; the model continues without search |
| LLM | `pause_turn` | Resend the history including `server_tool_use` blocks; counts as an iteration |
| LLM | `refusal`, `max_tokens`, `end_turn` with no submission | Stop codes `refused`, `truncated`, `no_submit` (one reminder first); nothing persisted |
| LLM | SDK `APIError` after retries | Stop `error`; usage so far logged; `run_log` row is `status=error`; the CLI continues with the next target |
| LLM | Invalid structured output | One repair attempt (compact Pydantic errors), else stop `invalid`; nothing persisted |
| LLM | `source_url` not in the seen-URL ledger, or a funding fact without a `note` | Treated as invalid output: same repair path, error lists up to 25 citable URLs |
| LLM | Iteration or USD cap | Stop `max_iter` or `budget`; no partial profile is written; `run_log` keeps stats and cost |
| LLM | Sources disagree | Record both, lower confidence, flag |
| Run classification (Phase 4) | Any non-`submitted` stop | `failure_category` set from the fixed taxonomy (see the [Phase 4 page](phases/phase-4-observability.md)) in the same commit as the stats and steps; raw error text stays as drill-down only |
| Exception outside the loop (Phase 4) | DB error after a `submitted` stop | `logged_run` marks the row `error`, falling back to `internal_error` if the category is still NULL |
| Observability tab (Phase 4) | No runs, no failures, a run with no steps, `stats == {}` | An explanatory message per state; never an exception |
| Eval run (Phase 5) | A golden company's enrichment fails | Counted as not submitted, never retried; cost still charged; the run continues |
| Eval run (Phase 5) | Batch cap reached before every entry ran | Remaining entries reported `skipped_budget`; run marked incomplete, exit 2 |
| Eval judge (Phase 5) | No verdict (batch exhausted, cap hit, invalid output) | Counted as `unjudged`, never as correct; no call is made once the batch is exhausted |
| Orchestrator (Phase 6) | An agent step fails | Recorded on its `run_log` row; the company's later steps still run unless enrich failed; result `partial` or `failed`; retried by the next invocation up to 3 failed attempts (D39) |
| Orchestrator (Phase 6) | 429 after the SDK's 5 retries | `RateLimitGate` pauses all workers 30 s and the step re-runs once; 5 trips stop the run (exit 1); `api_error` rows never exhaust a company |
| Orchestrator (Phase 6) | Batch cap reached, or SIGINT | Remaining steps and companies `skipped_budget` or `stopped`; in-flight calls finish; summary printed; exit 1 |
| Orchestrator (Phase 6) | Process killed mid-run | A `running` row older than 30 minutes is turned into `error` / `internal_error` at the next start and counts as a failed attempt |
| Verifier (Phase 6) | No independent second source found, or a verdict still fails the independence rules after one repair | Verdict `unverified` (reason in `observed` when rejected): a NULL-value `verification:<claim>` fact, confidence unchanged; the run is still `ok` |
| News agent (Phase 6) | No news found | Run is `ok` with zero items; not a failure |
| MCP tool | Bad input or DB error | Compact actionable text; never write to stdout |

## 4. Testing
- Unit tests for models, candidates, DB helpers; adapter tests with `httpx.MockTransport`; `streamlit.testing` smoke tests. The only live test is the Phase 1 hello call, skipped without a key.
- **Fake-client seam:** `run_agent` takes any object exposing `messages.create(**kwargs)`. `tests/fakes.py` provides a `ScriptedClient` that returns queued responses, records every request, and raises if the loop makes more calls than scripted; this is the seam the loop, tool and budget tests run against.
- Covered by tests: cost arithmetic, loop stop-reason handling (cache markers, repair path, iteration/USD caps, `pause_turn`, handler errors, unpriced models), tool wrapping and the URL ledger, enrichment schema derivation and provenance checks, and additive DB migration.
- No `-m live` enrichment test exists, so a plain `pytest` run never spends money.
- Phase 5: `UrlPolicy`/SSRF cases against an injected resolver; offline injection cases through `ScriptedClient` and `fixture_fetcher`; golden loader, metrics, number matcher, `BatchBudget`, judge and runner tests against synthetic data and fakes; live injection tests collected but skipped unless `SPROUT_RUN_LIVE_INJECTION=1`.
- Phase 4: the `ScriptedClient` seam proves step records (count equals iterations, summed usage matches the run total); DB tests cover the migration and backfill; `streamlit.testing` covers each dashboard state (the tab was not opened in a browser).
- Phase 6: status states, selector, retry and reaper against a temp SQLite file; a routing fake client (dispatch by company) drives the orchestrator with several worker threads (resume after a simulated kill, `gave_up`, budget skip, 429 gate, stop event, exit codes); threaded `BatchBudget` and concurrent SQLite and `DiskCache` writes; per-agent scripted tests including the classifier's independence from the prior category. The live orchestrator runs are recorded in `implementation-notes.md`; a live SIGINT and a live 429 were not exercised.
- Golden-set evals run on demand, not per push, to control cost.

## 5. Configuration
- Env plus `.env` via `get_settings()`: `ANTHROPIC_API_KEY`, `COMPANIES_HOUSE_API_KEY`, `SPROUT_BULK_MODEL`, `SPROUT_STRONG_MODEL`, `SPROUT_DB_PATH`, `SPROUT_CACHE_DIR`, `SPROUT_ENABLE_ACTIONS`.
- Secrets never committed; `.env`, `*.db`, `.cache/` are gitignored.
- Per-run USD and iteration caps (`--max-usd`, `--max-iterations`, defaults USD 0.13 and 12), `--effort` and `--strong`; the price table lives in `costs.py`, not env, so a run is reproducible from the commit. No search-backend setting: server-side search is hard-wired, and `build_tools` is the swap point.
- Phase 6 adds orchestrator CLI flags only (`--limit`, `--concurrency`, `--max-total-usd`, `--stale-days`, `--news-stale-days`, `--steps`, `--only`, `--no-prescreen`, `--force`, `--dry-run`) and no `Settings` field or env var; per-agent caps are constants next to each agent, listed in [section 9](#9-phase-6-agent-caps-and-run-budget). `get_engine` turns on WAL and a 30 s busy timeout for every connection.
- No migrations framework: `init_db` adds missing nullable columns additively; a non-additive change needs a DB reset, or Alembic if that becomes too limiting.
- Phases 4 and 5 added no `Settings` field; the eval DB path and batch cap are `run_evals` flags, `SPROUT_RUN_LIVE_INJECTION=1` is a test-only opt-in read by the live injection test, and `pyyaml` is already in the `dev` dependency group for the golden-set file.

## 6. Security
- Fetched content and Companies House data are wrapped in `<untrusted_content>` delimiters, the system prompt says it is data, and model output is validated and treated as untrusted. Search snippets are covered by the system-prompt rule only.
- Source URLs and `retrieved_at` are controlled by code via a seen-URL ledger, so injected text cannot make the model cite an invented page.
- `WebFetcher` is SSRF-aware; residual DNS-rebinding risk is accepted.
- The enrichment agent has no write or refresh tools; DB writes happen in our code after validation.
- Streamlit actions are off unless `SPROUT_ENABLE_ACTIONS=1`; public deployments are read-only with no keys.
- **Phase 5 additions (built):** `UrlPolicy` in `sources/web.py` blocks non-HTTP(S) schemes, non-standard ports, credentials in the URL, a denylist of local/internal hostnames, and any address that is not public once mapped IPv6/NAT64 is unwrapped (an `allow_hosts` override exists only for fixtures); a total fetch deadline; a runtime check (`ALLOWED_ENRICHMENT_TOOLS`) that keeps a state-changing tool out of the enrichment tool set; an injection suite with offline cases plus a live canary tier; the judge treats candidate text as untrusted and runs against a separate eval DB.
- **Phase 4 addition:** the truncated model text logged per step is untrusted; it's capped at 1,000 characters, never put into a prompt unwrapped, and rendered in Streamlit only via `st.code`/`st.text`/dataframe cells, never Markdown or raw HTML.
- **Phase 6 additions (built):** each of classify, news and verify has its own fail-closed `ALLOWED_*_TOOLS` set (no write or refresh tool in any); their inputs are second-order untrusted (profile text and RSS titles came from scraped pages), so they are wrapped in `<untrusted_content>` like fetched pages; every URL a news entry or verdict cites must be in that run's `SourceLedger`; the verifier cannot change a value, only a confidence and a note.
- **Residual risk:** a model that obeys an injected instruction and cites the injected page as its source passes code-level validation and the number-match check; only a live canary run, the golden comparison, or the Phase 6 verifier catch that. `fetch_page` can still be pushed toward a public attacker host with context in the query string; there are no secrets in context to leak. DNS rebinding between check and connection is an accepted residual risk.

## 7. Cost and observability
- `costs.py` converts API usage (input, output including thinking, cache read/write, server-side search) to USD; caps are enforced in `loop.py`'s `Budget` against the running total.
- Search is billed separately from tokens; `web_searches` is its own `stats` field and `max_uses` is a hard per-run cap. Search is the dominant cost component of a run, at roughly US$0.01 per search.
- `run_log.stats` is the current observability record.
- **Phase 4:** observability moved from one stats blob per run to queryable rows: `run_log_step` (one row per iteration) and `run_log.failure_category` (the fixed taxonomy), both read by the Observability tab. Historical runs appear in cost/failure trends but have no step rows.
- **Phase 5:** `BatchBudget` (see [4.8](#8-phase-5-eval-budget)) charges enrichment, judge, calibration and injection spend to one object, soft-capped at one response past the limit. The judge runs on the strong model, which is why it's limited to free-text fields.
- **Phase 6:** the same `BatchBudget`, now with a lock, caps all four agents' spend in one orchestrator invocation; the soft overshoot is one response per in-flight call. The batch `pipeline_run` row records its spend under `stats.spent_usd`, not `cost_usd`, so `cost_by_kind` does not count it twice.

## 8. Phase 5 eval budget

A planning estimate, not a measured full run (only a 2-company smoke run, about US$0.085, has been made); actual spend depends on model output and which optional evals are enabled.

| Component | Basis | Estimated spend per full eval |
|---|---|---:|
| Enrichment | 32 companies at the per-company mean (about US$0.0146) | US$0.47 |
| LLM judge | 51 short calls (25 business models plus 26 target users that have a sourced reference) | US$0.13 |
| Calibration | 12 triples, planning allowance | US$0.05 |
| Live injection tests | About 6 cases at the per-company average | US$0.08 |
| **Total** | | **About US$0.73** |

| Budget item | Amount | Meaning |
|---|---:|---|
| Eval allocation | US$5 | About 7 average-cost eval runs |
| Per-run cap (`BatchBudget.max_usd` for one invocation of `evals/run_evals.py`) | US$1.50 | Hard ceiling for one run, about 2x the US$0.73 estimate; confirmed (A19) |
| Reserve | US$4 | Unallocated |

The per-run cap is soft by at most one model response. `--score-only`, `--only`, `--limit` and `--skip-judge` reduce spend; `--strong` as the generator costs roughly five times more.

## 9. Phase 6 agent caps and run budget

Caps are constants next to each agent (`DEFAULT_BUDGET`, `CLASSIFY_BUDGET`, `NEWS_BUDGET`, `VERIFY_BUDGET`); each call's USD cap is clamped to the batch slice. Search is US$0.01 per call; token prices are in `costs.PRICES`. Measured means come from the live 50-company run (verify from the 3 companies that had a claim); the figures and their context are in [implementation-notes.md](../implementation-notes.md#phase-6---multi-agent-pipeline-at-scale).

| Agent | Model | Effort | Max iterations | Max USD per run | Max repairs | Searches (`max_uses`) | Measured mean per run |
|---|---|---|---:|---:|---:|---:|---:|
| enrich | bulk | low | 12 | 0.13 | 2 | 3 | US$0.023 |
| classify | bulk | low | 4 | 0.01 | 1 | none | US$0.0002 |
| news | bulk | low | 8 | 0.05 | 1 | 1 | US$0.011 |
| verify | strong | low | 8 | 0.10 | 1 | 2 | US$0.026 to 0.053 |

Caps are ceilings that catch a runaway, not expectations; they sum to US$0.29 per company, which bounds one `refresh_company`. The `BatchBudget` is the binding cap. Measured per-company cost was about US$0.03 to 0.04, with verify run on few companies because it needs a stage or funding claim. `--dry-run` uses fixed planning means (`ESTIMATED_STEP_USD` in `agents/orchestrator.py`) and prices verify on every company that needs it, so it overstates (the 50-company comparison is in the notes). The default `--max-total-usd` is US$5.00 (the acceptance ceiling); cumulative Phase 6 live spend is in the notes.
