# Risks and open questions

Part of the [Sprout architecture docs](README.md). See the [overview](1.%20overview.md), [cross-cutting concerns](4.%20cross-cutting.md) and [decisions](6.%20decisions.md) for the architecture these risks and ambiguities refer back to.

### 1. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Hallucinated or misattributed funding | High | Code-enforced sources, verifier, fabricated-funding gate at most 3%, pass the company number for disambiguation |
| Candidate pool noise inflates cost | High | Rank by `candidate_score`, cheap pre-screen, pilot a small batch first |
| Cost overrun | Medium | Hard caps per company, bulk routing, prompt caching. No batch-level cap yet; `BatchBudget` (D24) must land with the Phase 4 evals and the Phase 5 orchestrator must use it before running the full candidate set |
| Prompt injection via pages | High | Delimiters, no write tools, validation, existing size/type limits; offline and live-canary injection tests planned for Phase 4 |
| Runaway agent loops | Medium | Iteration and USD caps, per-run `max_uses` and fetch limits, last-iteration wrap-up message |
| Server-side search billing eats the per-company target | Low | `max_uses` is 3, searches are counted in `stats`; search dominates per-run cost but the total stays well under target |
| `pause_turn` or `server_tool_use` blocks mishandled | Medium | Append `response.content` unchanged; scripted-client tests cover pause and search turns |
| Same-name company confusion | High | Pass company number, incorporation date, SIC codes and locality in the user message; `lookup_companies_house` result is the identity anchor |
| Large pages or long loops inflate input cost | Medium | Tool-result character cap, prompt caching of the growing conversation |
| Pilot companies absent from the candidate pool | Low | CLI accepts a company number and creates the row from Companies House directly (`add_company_by_number`) |
| `fetch_page` URL chosen by the model can carry context to an attacker | Low | No secrets in context; `UrlPolicy` planned for Phase 4, but a public attacker host still passes |
| Non-deterministic model output: an occasional run ends `invalid` or `refused` | Medium | Single repair attempt; Phase 5 needs a retry policy (a failed latest attempt is retried; status is derived from `run_log`, D32) |
| Snippet-only claims cannot be audited | Medium | Code caps them at `medium` confidence and requires a note; the Phase 5 verifier is the real check |
| Funding coverage understated for non-USD figures | Low | Null is the safe failure; the note carries the original figure |
| Sparse funding data | Medium | "Not disclosed" valid; report coverage, never plot as zero |
| Scraping ToS and robots | Medium | Honour robots, per-host limits, store snippets and links; recheck before publishing |
| SDK and model drift | Medium | Pin model IDs explicitly; re-verify before swapping |
| Schema change without migrations | Medium | Reset during development; Alembic before the weekly job |
| Unattended weekly spend | Medium | Hard cap, console spend limit, failure notification |
| Small golden set | Medium | Report counts and percentages; record label date and source; dev and holdout split |
| Golden labels wrong, stale or circular | High | Draft from independent sources, user verifies each entry, only verified entries scored |
| Eval gate is flaky at n=30 | Medium | Set each gate one company below the baseline; re-run failing entries before calling a regression |
| Number-match fabrication check gives false flags or misses | Medium | Review every flag and tune before gating; unverifiable reported separately |
| Judge prefers fluent answers or disagrees with the user | Medium | Free text only, judge model differs from generator, reference-first rubric, calibration set |
| Passing the injection suite is read as safety | Medium | Documented residual risk (see [4.6 Security](4.%20cross-cutting.md#6-security)); no write tools; the Phase 5 verifier; live canary tier |
| SSRF policy gaps (encoded IPs, NAT64, rebinding) | Medium | Parametrised policy tests through an injected resolver; rebinding accepted |
| Logged model text carries injected content | Medium | Text blocks only, 1,000-character cap, never prompted unwrapped, rendered without Markdown or HTML |
| Phase 3 findings come from a biased sample (20 shell-style, name-matched candidates, 0 failures) | Medium | Treat the cost, repair-rate and tool-error figures as a floor; re-check on a mixed batch before setting Phase 4 gate values |
| Failure taxonomy too coarse to guide fixes | Low | Start at stop/error-type level; the step text and `run_log.error` carry the detail; split `invalid` only if it dominates |
| Schema grows again in Phase 5 | Low | Two additive items only (`run_log.company_id`, `company_news`); per-company status is derived, not stored (D32). Unique or indexed columns cannot be added by `init_db`, so dedupe in code |
| Mixed server and custom tool call in one turn gives an API 400 (reproduced with `--max-iterations 2`) | Medium | Unfixed; needs a live reproduction and a fix in the loop before the Phase 4 baseline (see the [Phase 2 page](phases/phase-2-enrichment.md#loop-contract-stop-reason-handling-covered-by-scripted-client-tests)) |
| SQLite single writer under the Phase 5 worker pool; a raw `cp` snapshot of a WAL database can miss the `-wal` file | Medium | Enable WAL and a busy timeout in `get_engine`, short per-company commits, snapshot with `VACUUM INTO` or the backup API |

### 2. Open ambiguities

| # | Phase | Open question | Current position |
|---|---|---|---|
| A1 | 1 / 5 | Candidate pool size and the rule for selecting which companies get enriched | Not pinned down |
| A2 | 2 / 7 | Search/fetch tooling differs across phases | Phase 2 resolved: server-side search only, all page reads through `WebFetcher` (D8). Still open for Phase 7: whether to replace `fetch_page` with an MCP server (see the [Phase 7 page](phases/phase-7-mcp-server.md)) |
| A3 | 2 | `CompanyProfile.stage` and a round's `stage` in `funding_rounds` can disagree | Precedence undefined |

| A5 | 2 | `Stage` values and funding-field units | Resolved: Series C/D/E/F are distinct values; funding fields are whole millions of USD |
| A6 | 2 | A re-run that nulls a previously valued field leaves both facts, and facts from URLs no longer cited remain | Proposed: the winning-value rule (see [4.1 Sourcing and provenance](4.%20cross-cutting.md#1-sourcing-and-provenance)): valued beats NULL, then most recent `retrieved_at`, then confidence. Must exist before Phase 6 |
| A7 | 3 | Logging tool inputs (e.g. the fetched URL) per step | Resolved: not logged; Phase 4 adds `stats.sources` (the seen-URL ledger) to the run stats |

| A9 | 3 | Granularity of a "step" | Resolved: one model response, which can call several tools; tokens and cost are not split per tool |

| A11 | 3 / 5 | `run_log` has no company link except inside `stats.company_id` | Deferred to the start of Phase 5: a nullable `run_log.company_id`, backfilled from `stats` (D32) |

| A13 | 4 / 5 | Ordering of evals vs. the multi-agent split | Resolved: evals (Phase 4) now precede the Phase 5 split |
| A14 | 4 | Fabricated-funding definition | Proposed (D21), not yet accepted |
| A15 | 4 | Last-round amount rule | Proposed (D22), not yet accepted |
| A16 | 4 | Injection-testing acceptance | Proposed: two tiers, offline + live canary (D26); needs sign-off |
| A17 | 4 | Golden-set labelling | Needs the user to verify entries from independent sources before tuning can start |
| A18 | 4 | URL policy: allowlist vs. deny-by-rule | Resolved: deny-by-rule in production since the agent must read arbitrary sites (D25); `allow_hosts` is for fixtures only |
| A19 | 4 | Eval spend estimate vs. proposed caps | US$0.70/run estimate vs. a US$1.50 per-invocation cap and US$5 allocation; needs confirming |
| A20 | 4 | Golden-set file format | Open: add `pyyaml` for YAML, or use stdlib `tomllib` with TOML |
| A21 | 4 | Source-URL "validity" | Resolved: reports both ledger membership (free) and liveness (opt-in request) |
| A22 | 4 | Judge model and calibration-set size | Sonnet judging Haiku, ~12 graded triples; a coarse signal until the set grows |
| A23 | 5 | Per-company status has no home in the current schema | Proposed (D32): derived from `run_log` plus `run_log.company_id`; no `enrichment_state` table |
| A24 | 5 | News has no company link, big-news score or type | Proposed (D33): `company_news` with `news_kind` and `summary` |
| A25 | 5 | Classifier "sub-category" has no schema field | Taxonomy stays flat and frozen |
| A26 | 5 | Discovery-agent output has no dedupe key when `company_number` is NULL | Open |
| A27 | 6 | "Funding history" is not supported by the current model | Resolved: the `funding_round` table (Phase 2), one sourced row per round; replaced on each save, so no history across runs |
| A28 | 6 / 8 | Snapshot delivery mechanism for read-only deployments | Undecided |
| A29 | 6 | Dashboard is meant to be read-only but the console can spend API quota | Needs separating or removing before deploy |
| A30 | 6 | The optional Ask box duplicates MCP access | Needs a read-only guarantee and rate limit |
| A31 | 7 | `refresh_company` sync/async, cooldown and payer | Unspecified; the cooldown can read `run_log.company_id` and `started_at` |
| A32 | 5 | Nothing marks a candidate as not a real AI startup (shells, consultancies); 12 of the 20 highest-scored candidates enriched to `Other` with 2 to 3 sourced facts | Open: pre-screen before enrichment, or flag after (a nullable `company` column). Decide with candidate selection (A1) |

### 3. Open items by phase
- **Phase 2:** profile review by the user, a console-invoice check of the search price, a decision on the tool-call 400, and the cost-split confirmation (A12).
- **Phase 3:** decide the six proposed Phase 4 adjustments (A10); A7 to A9 are settled as built.
- **Phase 4:** label and verify the golden set (A17, critical path); approve the fabricated-funding definition (A14), last-round rule (A15) and two-tier injection acceptance (A16); choose `pyyaml` or TOML (A20); confirm the eval budget and cap (A19, A22).
- **Before Phase 5:** the two schema additions (`run_log.company_id`, `company_news`); WAL and busy timeout; a retry policy; candidate pre-screen and selection (A1, A32); concurrency model for the sync client.
- **Before Phase 6:** the winning-value rule (A6) and the shared service layer (D29). **Before Phase 7:** define `refresh_company` (A31).
- **Before Phases 6 and 8:** snapshot delivery (A28); data licensing and robots recheck.
