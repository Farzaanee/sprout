# Risks and open questions

Part of the [Sprout architecture docs](README.md). See the [overview](1.%20overview.md), [cross-cutting concerns](4.%20cross-cutting.md) and [decisions](6.%20decisions.md) for the architecture these risks and ambiguities refer back to.

### 1. Risks

See `project-plan.md`'s risk list for the original funding-sparsity and scraping/ToS risks; not repeated here.

| Risk | Severity | Mitigation |
|---|---|---|
| Hallucinated or misattributed funding | High | Code-enforced sources, fabricated-funding gate at most 3%, pass the company number for disambiguation |
| Candidate pool noise inflates cost and thins profiles | High | Pre-screen on active officer count plus an active director role, and a tighter `assess()` keyword gate (D34), cheap and free. Live pilot found the original officer-count-only filter too loose (34 of 50 working-set companies ended `Other`); the director/keyword tightening is not yet revalidated live (A1, A32) |
| Cost overrun (see `project-plan.md` risks for the base mitigation) | Medium | `BatchBudget` (D24) caps `run_evals` and opt-in `sprout.enrich --max-total-usd`; the Phase 6 orchestrator always uses it (default US$5.00) with a lock, one cap over every agent (D38); the live runs stayed well under it |
| Prompt injection via pages | High | Delimiters, no write tools, validation, existing size/type limits; offline injection tests and the live canary tier (9 of 9 passed) |
| Runaway agent loops | Medium | Iteration and USD caps, per-run `max_uses` and fetch limits, last-iteration wrap-up message |
| Server-side search billing eats the per-company target | Low | `max_uses` is 3, searches are counted in `stats`; search dominates per-run cost but the total stays well under target |
| `pause_turn` or `server_tool_use` blocks mishandled | Medium | Append `response.content` unchanged; scripted-client tests cover pause and search turns |
| Same-name company confusion | High | Pass company number, incorporation date, SIC codes and locality in the user message; `lookup_companies_house` result is the identity anchor |
| Large pages or long loops inflate input cost | Medium | Tool-result character cap, prompt caching of the growing conversation |
| Pilot companies absent from the candidate pool | Low | CLI accepts a company number and creates the row from Companies House directly (`add_company_by_number`) |
| `fetch_page` URL chosen by the model can carry context to an attacker | Low | No secrets in context; `UrlPolicy` (Phase 5) blocks non-public targets, but a public attacker host still passes |
| Non-deterministic model output: an occasional run ends `invalid` or `refused` | Medium | Single repair attempt; the Phase 6 retry policy re-runs a failed latest attempt up to 3 times across runs (D39; status derived from `run_log`, D32) |
| Snippet-only claims cannot be audited | Medium | Code caps them at `medium` confidence and requires a note; the number-match check and the golden set are the audit |
| Funding coverage understated for non-USD figures | Low | Null is the safe failure; the note carries the original figure |
| SDK and model drift | Medium | Pin model IDs explicitly; re-verify before swapping |
| Schema change without migrations | Medium | Reset during development; Alembic before the weekly job |
| Unattended weekly spend | Medium | Hard cap, console spend limit, failure notification |
| Small golden set (32 entries; one company is about 3 points) | Medium | Report counts and percentages; record label date and source; dev and holdout split, gates on the full set only |
| Golden labels wrong, stale or circular | High | Drafted from independent sources, all 32 verified by the user, only verified entries scored; a wrong `company_number` would score the wrong company, so the report shows the resolved Companies House name (caught and fixed once, on BenevolentAI, see [learnings-ph-5.md](../learnings/learnings-ph-5.md)) |
| Eval gate is flaky at n=32 | Medium | Set each gate one company below the baseline; re-run failing entries before calling a regression |
| Number-match fabrication check gives false flags or misses | Medium | Review every flag and tune before gating; unverifiable reported separately |
| Judge prefers fluent answers or disagrees with the user | Medium | Free text only, judge model differs from generator, reference-first rubric, calibration set |
| Passing the injection suite is read as safety | Medium | Documented residual risk (see [4.6 Security](4.%20cross-cutting.md#6-security)); no write tools; live canary tier |
| SSRF policy gaps (encoded IPs, NAT64, rebinding) | Medium | Parametrised policy tests through an injected resolver; rebinding accepted |
| Logged model text carries injected content | Medium | Text blocks only, 1,000-character cap, never prompted unwrapped, rendered without Markdown or HTML |
| Phase 4 findings come from a biased sample (20 shell-style, name-matched candidates, 0 failures) | Medium | Treat the cost, repair-rate and tool-error figures as a floor; re-check on a mixed batch before setting Phase 5 gate values |
| Failure taxonomy too coarse to guide fixes | Low | Start at stop/error-type level; the step text and `run_log.error_message` carry the detail; split `invalid` only if it dominates |
| Schema grows again | Low | Phase 6 added no table or column: both schema items (`run_log.company_id`, `company_news`) were built earlier (D32, D33) and per-company status is derived, not stored. Unique or indexed columns cannot be added by `init_db`, so dedupe in code |
| Mixed server and custom tool call in one turn gave an API 400 (reproduced with `--max-iterations 2`) | Low | Fixed in `loop.py` (an orphaned `server_tool_use` block is dropped before the next request) and verified live with a deterministic `iteration_cap` run. |
| SQLite single writer under the Phase 6 worker pool; a raw `cp` of a WAL database can miss the `-wal` file; committed `data/eval.db` and the snapshot must be cleanly closed | Medium | WAL and a 30 s busy timeout in `get_engine`, no write transaction across a model call, a `*.db-wal`/`*.db-shm` gitignore entry; `make snapshot` (`scripts/make_snapshot.py`) uses `VACUUM INTO` and verifies the copy (D38) |
| Spend overshoots the batch cap under concurrency | Low | Soft by one response per in-flight call (about `concurrency x US$0.02`); atomic `try_slice`; the caps leave the ceiling headroom (D38) |
| News false matches (same-name companies), duplicates, over-flagged "big" items and sparse coverage | Low | Model checks each search result against the company's one-liner; ledger-checked URLs; `_settle` collapses same-kind, same-date entries from one submission. The D28 hand-check (A34) found no company mismatches; the rubric still over-flags some leadership items (narrowed) and some items lack a date |
| 429 storm at concurrency 4 | Medium | SDK `max_retries=5`, shared pause gate, one re-run, stop after 5 trips (D38); `api_error` never exhausts a company. Zero trips occurred in a real run; the gate/retry path was exercised live with a simulated 429 (trip, 30s pause, one retry), confirming the mechanics outside of unit tests |
| Per-worker rate limiters loosen shared-host politeness | Low | Concurrency capped at 8; Companies House use is about 3 calls per company; documented in D38 |
| Two workers write one cache key and the second `os.replace` fails | Low | Unique temp name in `DiskCache.put`; the tool handler already turns an exception into an error result |
| `profile_gaps` and the console line count an explicit "not disclosed" as incomplete | Low | Misleading progress signal only (48 of 50 shown incomplete); the stored data is correct. Count only never-attempted fields instead |
| Hard second SIGINT leaves the `pipeline_run` row `running`, blocking a restart for 30 minutes | Low | `--force` overrides the lock; `reap_abandoned` now reaps stale batch rows (`pipeline_run`, `companies_ingest`) past the timeout too, not just per-company rows. Exercised with a live double-SIGINT (hard kill), a live single-SIGINT (graceful drain), and a live 429 (simulated, real gate/retry code path) |
| A read-only deployment of the snapshot cannot open it: the file is in WAL mode, and `init_db` plus a normal connection write even on a read (`attempt to write a readonly database` from a read-only directory; a writable copy works) | Medium | Phase 7: when the database path is not writable, open it with a `mode=ro&immutable=1` URI and skip `init_db` (verified to read the snapshot from a read-only directory). Phase 9 Dockerfile and hosting must keep the snapshot cleanly checkpointed, which `make snapshot` already guarantees |
| Legacy rows in the snapshot: `category` values outside the `Category` enum (6 "AI models and applications") and unused `verification:*` facts | Low | Phase 7 reads category options from the data and shows fact fields from an allowlist; re-enriching a company replaces its label |
| Enrichment cost rose with the prompt (about US$0.015 in Phases 3 and 4, about US$0.023 to 0.026 now) | Low | Treat the estimate as a ceiling; set caps from measured figures ([cross-cutting 9](4.%20cross-cutting.md#9-phase-6-agent-caps-and-run-budget)) |

### 2. Open ambiguities

| # | Phase | Open question | Current position |
|---|---|---|---|
| A1 | 2 / 6 |  Candidate pool size and the rule for selecting which N companies get enriched in one run | Resolved (D34, D39): `--limit N` takes the first N pre-screen survivors by `candidate_score`, bounded by `--max-total-usd`. The pilot found the officer-count-only pre-screen too loose, and name-matched candidates tie on score so rank falls back to `id` (see the [notes](../implementation-notes.md#d34-pre-screen-validation-a1)). Pre-screen since tightened with a director-role check and a stricter `assess()` keyword gate (D34); not yet revalidated live, and the score-tie fallback to `id` is unchanged |
| A2 | 3 / 8 | Search/fetch tooling differs across phases | Phase 3 resolved (D8): Anthropic's server-side `web_search` (`max_uses` 3) for search, no server-side `web_fetch`; every page read goes through the custom `fetch_page` tool, which wraps `WebFetcher` so robots, SSRF, size and cache protections apply to every page the agent reads. Still open for Phase 8: the enrichment agent there calls an off-the-shelf MCP fetch server instead of `fetch_page` directly, which would bypass those protections unless `WebFetcher` is wrapped behind the MCP interface or the swap is kept behind a flag (see the [Phase 8 page](phases/phase-8-mcp-server.md)) |
| A3 | 3 | `CompanyProfile.stage` and a round's `stage` in `funding_rounds` can disagree | Resolved: `validate_submission` rejects a mismatch against the most recently announced round as a repairable error, same path as other provenance problems (see the [Phase 3 page](phases/phase-3-enrichment.md#stage-two-independent-fields-reconciled-by-one-repair-a3)). Not checked when no round has an `announced` date, or on a later read of already-saved data |
| A4 | 3 / 8 | Keeping `refresh_company` out of the enrichment agent's tool set | Resolved by design (D26, Phase 5 build): `ALLOWED_ENRICHMENT_TOOLS` checked at runtime and in a test. Phase 6 added the same fail-closed check per agent (`ALLOWED_NEWS_TOOLS`). Phase 8 must update both sets deliberately if `fetch_page` is replaced |
| A5 | 3 | `Stage` values and funding-field units | Resolved: Series C/D/E/F are distinct values; funding fields are whole millions of USD |
| A6 | 3 | A re-run that nulls a previously valued field leaves both facts, and facts from URLs no longer cited remain | The winning-value rule is implemented as `db.winning_facts` (see the [Phase 3 page](phases/phase-3-enrichment.md#the-winning-value-rule-a6)): valued beats NULL, then most recent `retrieved_at`, then confidence. Called by the Phase 6 agent inputs, `status.profile_gaps` and the evals; the Phase 7 profile read must use it too |
| A7 | 4 | Logging tool inputs (e.g. the fetched URL) per step | Resolved: not logged; `stats.sources` (the seen-URL ledger) is in the run stats (Phase 5) |
| A8 | 4 | Failure taxonomy granularity | Resolved: stays at eight categories; `invalid_output` is not split by sub-reason |
| A9 | 4 | Granularity of a "step" | Resolved: one model response, which can call several tools; tokens and cost are not split per tool |
| A10 | 4 | Phase 4 findings feed the Phase 5 design | Resolved. All six proposed adjustments are addressed: stratification, repair-rate metric and the profiles-submitted floor are in the Phase 5 design; the cost gate (D36) and judge input (D37, `tool_error_text`) are decided; the mixed-tool-call 400 is fixed in `loop.py`. The sample was shell-style candidates, so gate values should still be set from the Phase 5 baseline |
| A11 | 4 / 6 | `run_log` has no company link except inside `stats.company_id` | Resolved (D32): `run_log.company_id` is a real, indexed, nullable column, backfilled from `stats` |
| A12 | 5 | Cost allocation across evals, repeated runs and prompt iteration | Not itemized against the total budget (see [4.8 Phase 5 eval budget](4.%20cross-cutting.md#8-phase-5-eval-budget)) |
| A13 | 5 / 6 | Ordering of evals vs. the multi-agent split | Resolved: evals (Phase 5) now precede the Phase 6 split |
| A14 | 5 | Fabricated-funding definition | Resolved: number-match against the cited page text as the model saw it, within 1 percent (D21) |
| A15 | 5 | Last-round amount rule | Resolved and confirmed (D22) |
| A16 | 5 | Injection-testing acceptance | Resolved and confirmed: two tiers, offline + live canary (D26) |
| A17 | 5 | Golden-set labelling | Resolved: user has verified the entries in `evals/golden.yaml` |
| A18 | 5 | URL policy: allowlist vs. deny-by-rule | Resolved: deny-by-rule in production since the agent must read arbitrary sites (D25); `allow_hosts` is for fixtures only |
| A19 | 5 | Eval spend estimate vs. proposed caps | Resolved: about US$0.73/run estimate, US$1.50 per-run cap, US$5 total allocation, all confirmed |
| A20 | 5 | Golden-set file format | Resolved: YAML, with `pyyaml` added to the `dev` dependency group |
| A21 | 5 | Source-URL "validity" | Resolved: reports both ledger membership (does the URL match a known, trusted source pattern ) (free) and liveness (does the URL actually resolve right now) (opt-in request) |
| A22 | 5 | Judge model and calibration-set size | Resolved: Sonnet judging Haiku, 12 user-confirmed graded triples in `evals/judge_calibration.yaml`; a coarse signal until the set grows |
| A23 | 6 | Per-company status has no home in the current schema | Resolved (D32): derived from `run_log` plus `run_log.company_id`; no `enrichment_state` table |
| A24 | 6 | News has no company link, big-news score or type | Resolved: schema (D33) built in Phase 3, populated by the Phase 6 news agent (one web search, model-scored); 7 of 50 live companies have items |
| A27 | 7 | "Funding history" is not supported by the current model | Resolved: the `funding_round` table (Phase 3), one sourced row per round; replaced on each save, so no history across runs |
| A28 | 7 / 9 | Snapshot delivery mechanism for read-only deployments | Resolved (D40): `make publish-snapshot` after an enrichment pass commits and pushes `data/sprout_snapshot.db`; the `snapshot` CI workflow verifies it on push |
| A29 | 7 | Dashboard is meant to be read-only but the console can spend API quota | Resolved: the console tab is removed; the dashboard has no write or spend path (a test checks it imports no ingest, hello, agents or `anthropic` code) |
| A30 | 7 | The optional Ask box duplicates MCP access | Resolved: deliberately skipped (see the [Phase 7 page](phases/phase-7-dashboard.md)); nothing to guard |
| A31 | 8 | `refresh_company` sync/async, cooldown and payer | Unspecified; the cooldown can read `run_log.company_id` and `started_at` |
| A32 | 6 | Not a real AI startup (shells, consultancies); 12 of the 20 highest-scored candidates enriched to `Other` with 2 to 3 sourced facts | Resolved in part (D34): pre-screen on active officer count plus an active director role, and a stricter `assess()` keyword gate, before enrichment; genuine single-officer startups are a known false-reject case. The live pilot found the officer-count-only version too loose (A1); the tightening is not yet revalidated live |
| A34 | 6 | News has no golden labels, so D28 cannot be applied to it by metric | Resolved: hand-checked against the rubric (24 items from a shell-heavy pilot, then 24 more from 8 golden-set startups after a targeted `--only --steps news` run). 40/40 items were about the right company, clearing the D28 90% keep bar. Found and fixed: the leadership rule now excludes board/director/advisor appointments without a C-suite title, and same-kind same-date entries from one submission are collapsed (`_settle`). Still open: cross-date duplicate coverage of one event from different outlets (not caught by the exact-date collapse), and some items still lack a `published` date |

- **Phase 5:** done. See the [status table](7.%20status.md) and the [Phase 5 page](phases/phase-5-evals-guardrails.md).

Open: tightening the candidate pool (A1, D34), and the weak spots listed on the [Phase 6 page](phases/phase-6-multi-agent.md#known-weak-spots-and-open-items). - **Before Phase 7:** done. The shared layer is `sprout/queries.py` (D29) and `get_profile` applies the winning-value rule (A6) and joins `company_news`. `status.profile_gaps` still counts a NULL (not disclosed) fact as a gap, so the progress signal is unchanged. **Before Phase 8:** define `refresh_company` (A31).
- **Before Phases 7 and 9:** data licensing and robots recheck.
