# Sprout: Learnings - Phase 6 - Multi-agent pipeline at scale

**Planned:** multi-agent orchestration patterns (supervisor/worker, specialisation), model routing for cost, concurrency with `asyncio`, resumable pipelines, failure isolation.

**Actual (the D28 check for the news agent has not been run):**

| Topic | Key learning |
| --- | --- |
| Threads over native async | Agents call blocking SQLite, HTTP and ORM code, so concurrency is `asyncio` plus `to_thread` with one resource bundle per worker (own `HttpClient`, fetcher, Companies House client, `Session`). Only the Anthropic client is shared, because it is the only thread-safe one. ORM objects and sessions must never cross threads. |
| Derived status, not a state table | Per-step status is computed from `run_log` (`status.py`), so resume needs no extra table and cannot drift from what actually ran. Restarting the same command skipped 49 of 50 companies and spent nothing. The cost is that a killed process leaves `running` rows, so a reaper (`reap_abandoned`) must turn them into failed attempts at startup. |
| `api_error` is not the company's fault | Failed attempts that count towards the 3-attempt cap exclude `api_error` rows. Otherwise a rate-limit burst would permanently give up healthy companies. |
| A shared budget needs an atomic slice | With four workers, check-then-charge on `BatchBudget` races. `try_slice(cap)` takes `min(cap, remaining)` under a lock and becomes that call's `max_usd`, so overshoot is bounded by one in-flight response per worker. |
| SDK retries before your own | The client is built with `max_retries=5`, so a 429 that reaches the orchestrator has already survived backoff. Only then does the shared `RateLimitGate` pause every worker and re-run the step once. The gate and the 5-trip stop were never triggered live (0 trips), so they are covered by tests only. |
| SQLite under concurrent writers | WAL plus a 30 s busy timeout is enough only because no write transaction is held across an API call: `run_recorded` commits the run row first and writes results afterwards. WAL also means snapshots must use `VACUUM INTO` or the backup API, not a file copy. |
| `DiskCache.put` was not thread-safe | A fixed temp filename collided once workers shared the cache. The temp name now includes pid and thread id. |
| Specialisation is for isolation | A failed news step leaves the profile intact and has its own `run_log` row, cost and failure category. Per company the whole pipeline cost about US$0.03 to 0.04 against US$0.077 planned, with enrichment 68% of spend. Quality benefit is unproven until the D28 check is run, so the news agent is not yet shown to help. |
| Pilot before the batch paid off | The 12-company pilot exposed a news rubric that flagged most items as big. The rubric change helped only a little (16 of 24 items still big). |
| Candidate pool quality | The pilot pool was too noisy: 5 of the 12 pilot companies were still shells or unclear. Name-keyword matches all tie at `candidate_score` 4, so ranking falls back to `id`, and thin profiles are largely the pool's property, not the pipeline's. |
| `--limit` is a working set | `--limit N` bounds the set, not the new work, so rerunning completes the same N companies and never reaches further down the pool. This is what makes resume idempotent, and it means a larger run needs a larger `--limit`. |
| Name matching for news | RSS matching by whole-word company name needs legal suffixes stripped and a generic-name guard (`match_name` returns `None`), otherwise single-word names match unrelated stories. Title-token Jaccard dedupe still leaves cross-outlet near-duplicates (3 groups in 24 items), and 9 of 24 items have no published date. |

## Enrichment coverage investigation: 70 non-golden companies

Investigated on 2026-11-10 using the persisted production snapshot and eval database, compared with the full 32-company evaluation recorded on 2026-11-08. Matching by Companies House number found that 14 of the 84 enriched production companies belong to the golden set, not all 32. The production figures below exclude those 14, leaving 70 non-golden companies; eval figures still describe the separate 32-company eval database. These observations describe the stored results, not a new enrichment run. The earlier Phase 6 pilot and batch learnings above retain their original historical cohorts.

| Finding | Evidence | Learning / follow-up |
| --- | --- | --- |
| Production coverage is low | Of 70 non-golden enriched companies, 41 are `Other` (58.6%). Stage has a value for only 2/70 (2.9%), leaving 68 missing (97.1%). Valuation has no values: 70/70 missing (100%). All five populated production valuations belong to excluded golden-set companies. | Report field coverage separately from correctness and pipeline completion. An accepted profile can still contain mostly null values. |
| 75% stage accuracy does not mean 75% stage coverage | The eval's 24/32 correct stages comprise 12 correct `Unknown` answers and 12 correct known stages. Among the 20 entries with a known reference stage, accuracy is 12/20 (60%); populated stage coverage is 12/32 (37.5%). [`stage_correct`](../../evals/metrics.py) accepts null when the reference is `Unknown`. | Add known-stage accuracy and populated-stage coverage alongside overall accuracy so correct abstentions do not obscure extraction misses. **Done:** both are now reported (12/20 and 12/32 on the stored eval DB). |
| Valuation coverage was not evaluated | The 75% metric scores stage only. The golden set's valuation labels are reference data, not scored by the current eval metrics. | Do not extrapolate stage accuracy to valuation. Add a dedicated valuation metric before claiming valuation quality. **Done:** on the stored eval DB valuation is correct for 5 of the 15 entries with a reference (33.3%) and populated for 10 of 32 (31.2%), well below stage accuracy. |
| The production and eval cohorts are different | The [golden set](../../evals/golden.yaml) deliberately includes 24 genuine AI startups and eight non-startup/control entities. Production uses legal-name keywords and SIC codes, ranked by candidate score. Among the 70 non-golden profiles, only 28/70 (40%) have a website recorded and 30/70 (42.9%) have a business model; 36 of the 41 `Other` profiles have no website recorded. | Candidate scores are not evidence of an operating, funded startup. Improve candidate sourcing and validate candidate selection on a representative production sample; missing recorded evidence alone does not prove a company is a shell. |
| The former classifier increased `Other` | Across the 48 distinct non-golden classified companies in the historical snapshot, enrichment originally assigned 16 `Other`; the latest classifications assigned 32. Eighteen companies moved into `Other` and two moved out. The other two classified companies belong to the golden set and are excluded here. The former classifier defaulted to `Other` for insufficient evidence and treated `Unclear`, `Closed` or `Dormant (shell)` status as evidence for `Other`. | The rule conflated unknown activity, operating status and industry category. The classifier has since been removed from the pipeline; the historical snapshot does not measure the current pipeline's category quality. |
| The cited eval did not validate classification | The persisted 32-company eval contains no classifier runs, unlike the historical production pipeline where classification overwrote enrichment's category. | Enrichment-only accuracy did not measure the former end-to-end pipeline. The classifier has since been removed. |
| Some missing stages are extraction inconsistencies | Production stores a sourced `Series A` funding round for Neural Foundry while its top-level stage is null. The [submission validator](../../src/sprout/agents/enrich.py) checks disagreement with the latest dated round only when the top-level stage is non-null. | Reconcile missing stages with sourced rounds under an explicit latest-round policy, with regression tests; not every missing stage is explained by the candidate pool. **Done for new runs:** `validate_submission` now fills a null stage from the latest dated round (confidence capped at `medium`, with a note), with no fill for an `Unknown` latest stage, no dated round, or conflicting stages tied on the latest date. Existing profiles are unchanged until re-enriched or backfilled; the effect on production coverage is not yet measured. |
| Prioritize diagnosis before another large run | The observed gap combines metric definitions, cohort selection, historical classifier behavior and genuine extraction misses. Their individual contribution cannot be established from overall missing-field percentages alone. | Separate coverage from accuracy and improve candidate selection before paying for another large enrichment batch. |
