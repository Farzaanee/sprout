# Cross-cutting concerns

Part of the [Sprout architecture docs](README.md). See the [overview](1.%20overview.md) for the architecture and data model these concerns apply to, and [decisions](6.%20decisions.md) / [risks](5.%20risks.md) for the accompanying decision log and risk register.

## 1. Sourcing and provenance
- `Sourced[T]` rejects a non-null value with no `source_url`. `value=None` means "not disclosed" and must render as such, never zero or blank.
- Per-fact `retrieved_at` (UTC) supports a staleness policy; registry facts can lag up to 7 days via the HTTP cache.
- Multiple sources per field can coexist, which lets a verifier record disagreement.
- Not provenance-bearing: `category`, `news_item` (source is the feed), free-text fields.
- The winning-value rule (A6), for which value wins when a field has several facts: a valued fact beats a NULL one, then the most recent `retrieved_at`, then the higher `confidence`; confidence is not first, because a stale high-confidence fact would otherwise beat a fresher medium one after a re-run. Implemented as `db.winning_facts`; not yet called by any reader (see the [Phase 2 page](phases/phase-2-enrichment.md#the-winning-value-rule-a6)). "Sources disagree" is surfaced only between facts from the same refresh, since an older fact from a superseded run is stale, not a disagreement.
- Funding rounds are tracked in a dedicated `funding_round` table, one row per round, each sourced independently; `save_profile` replaces a company's rounds on every save, so there is no history across runs, only within the latest one.
- SQLite treats NULLs as distinct in UNIQUE constraints; `save_fact` dedupes in application code rather than relying on the constraint.

## 2. Agent orchestration
- A deterministic supervisor selects companies and runs workers with `asyncio` under a concurrency limit.
- Per company: enrich, then classify (bulk model), news, then verify (only for funding or stage claims). Classifier and news can run in parallel.
- Models: bulk `claude-haiku-5-5` for extraction/classification; strong `claude-sonnet-5-5` for verification/synthesis; overridable via `SPROUT_BULK_MODEL` / `SPROUT_STRONG_MODEL`. An unpriced override fails closed in `costs.py`.
- The enrichment loop (see the [Phase 2 page](phases/phase-2-enrichment.md)) uses `tool_choice: auto`, explicit effort, a prompt-cached conversation, and handles `pause_turn`/`server_tool_use`, under per-run caps on iterations, USD and searches. There is no per-run fetch cap and no batch-level cap yet, and a mixed server and custom tool call in one turn can produce an API 400 (see the [Phase 2 page](phases/phase-2-enrichment.md#loop-contract-stop-reason-handling-covered-by-scripted-client-tests)).
- Resume: the unit of work is a company; one transaction per company. Per-company status is derived from `run_log` (latest attempt, `failure_category`, newest ok `finished_at`; see the [data model](2.%20data-model.md#planned-additions-phase-5)), not stored: a company with a fresh ok run is skipped and one whose latest attempt failed is retried.
- A company failure is recorded on its `run_log` row (`failure_category`) and the run continues. Target at least 85% `ok`.

## 3. Error handling

| Boundary | Failure | Behaviour |
|---|---|---|
| Companies House / RSS | 429 or 5xx | Retry with backoff and `Retry-After`, then `FetchError` |
| Companies House | 404 | Cached, treated as no result |
| RSS | One feed broken | Reported in `failed_feeds`, exit 1, others continue |
| Web fetch | robots, private IP, content type, URL policy violation | `FetchBlockedError`, returned to the model as a tool error |
| Web fetch | robots.txt unreachable | Refuse |
| Web fetch | Response slower than `max_seconds` (Phase 4, planned) | `FetchError`, not retried |
| Web fetch | Page larger than the tool-result cap | Truncated to 8,000 characters (`TOOL_RESULT_MAX_CHARS`) with a "[truncated]" marker; `WebFetcher` caps at 20,000 characters |
| Companies House tool | 404 or invalid number | Returned to the model as a "no such company" error string; not retried |
| Server-side search | `max_uses_exceeded`, `unavailable`, rate limit | Arrives as an error result block, not an exception; the model continues without search |
| LLM | `pause_turn` | Resend the history including `server_tool_use` blocks; counts as an iteration |
| LLM | `refusal`, `max_tokens`, `end_turn` with no submission | Stop codes `refused`, `truncated`, `no_submit` (one reminder first); nothing persisted |
| LLM | SDK `APIError` after retries | Stop `error`; usage so far logged; `run_log` row is `status=error`; the CLI continues with the next target |
| LLM | Invalid structured output | One repair attempt (compact Pydantic errors), else stop `invalid`; nothing persisted |
| LLM | `source_url` not in the seen-URL ledger, or a funding fact without a `note` | Treated as invalid output: same repair path, error lists up to 25 citable URLs |
| LLM | Iteration or USD cap | Stop `max_iter` or `budget`; no partial profile is written; `run_log` keeps stats and cost |
| LLM | Sources disagree | Record both, lower confidence, flag |
| Run classification (Phase 3) | Any non-`submitted` stop | `failure_category` set from the fixed taxonomy (see the [Phase 3 page](phases/phase-3-observability.md)) in the same commit as the stats and steps; raw error text stays as drill-down only |
| Exception outside the loop (Phase 3) | DB error after a `submitted` stop | `logged_run` marks the row `error`, falling back to `internal_error` if the category is still NULL |
| Observability tab (Phase 3) | No runs, no failures, a run with no steps, `stats == {}` | An explanatory message per state; never an exception |
| Eval run (Phase 4, planned) | A golden company's enrichment fails | Counted as not submitted; cost still charged; the run continues |
| Eval run (Phase 4, planned) | Batch cap reached before every entry ran | Remaining entries reported `skipped_budget`; run marked incomplete, exit 2 |
| Eval judge (Phase 4, planned) | No verdict | Counted as `unjudged`, never as correct |
| MCP tool | Bad input or DB error | Compact actionable text; never write to stdout |

## 4. Testing
- Unit tests for models, candidates, DB helpers; adapter tests with `httpx.MockTransport`; `streamlit.testing` smoke tests. The only live test is the Phase 0 hello call, skipped without a key.
- **Fake-client seam:** `run_agent` takes any object exposing `messages.create(**kwargs)`. `tests/fakes.py` provides a `ScriptedClient` that returns queued responses, records every request, and raises if the loop makes more calls than scripted; this is the seam the loop, tool and budget tests run against.
- Covered by tests: cost arithmetic, loop stop-reason handling (cache markers, repair path, iteration/USD caps, `pause_turn`, handler errors, unpriced models), tool wrapping and the URL ledger, enrichment schema derivation and provenance checks, and additive DB migration.
- No `-m live` enrichment test exists, so a plain `pytest` run never spends money.
- Planned for Phase 4: `UrlPolicy`/SSRF cases against an injected resolver; offline injection cases through `ScriptedClient` and `fixture_fetcher`; golden loader, metrics, number matcher, `BatchBudget` and judge tests against synthetic data; one live-gated injection test behind `SPROUT_RUN_LIVE_INJECTION=1`.
- Phase 3: the `ScriptedClient` seam proves step records (count equals iterations, summed usage matches the run total); DB tests cover the migration and backfill; `streamlit.testing` covers each dashboard state (the tab was not opened in a browser).
- Golden-set evals run on demand, not per push, to control cost.

## 5. Configuration
- Env plus `.env` via `get_settings()`: `ANTHROPIC_API_KEY`, `COMPANIES_HOUSE_API_KEY`, `SPROUT_BULK_MODEL`, `SPROUT_STRONG_MODEL`, `SPROUT_DB_PATH`, `SPROUT_CACHE_DIR`, `SPROUT_ENABLE_ACTIONS`.
- Secrets never committed; `.env`, `*.db`, `.cache/` are gitignored.
- Per-run USD and iteration caps (`--max-usd`, `--max-iterations`, defaults USD 0.13 and 12), `--effort` and `--strong`; the price table lives in `costs.py`, not env, so a run is reproducible from the commit. No search-backend setting: server-side search is hard-wired, and `build_tools` is the swap point.
- No migrations framework: `init_db` adds missing nullable columns additively; a non-additive change needs a DB reset, or Alembic if that becomes too limiting.
- Phase 3 added no environment variables and Phase 4 (planned) adds none; the eval DB path and batch cap are `run_evals` flags, and `pyyaml` joins the `dev` dependency group for the golden-set file.

## 6. Security
- Fetched content and Companies House data are wrapped in `<untrusted_content>` delimiters, the system prompt says it is data, and model output is validated and treated as untrusted. Search snippets are covered by the system-prompt rule only.
- Source URLs and `retrieved_at` are controlled by code via a seen-URL ledger, so injected text cannot make the model cite an invented page.
- `WebFetcher` is SSRF-aware; residual DNS-rebinding risk is accepted.
- The enrichment agent has no write or refresh tools; DB writes happen in our code after validation.
- Streamlit actions are off unless `SPROUT_ENABLE_ACTIONS=1`; public deployments are read-only with no keys.
- **Phase 4 additions (planned):** `UrlPolicy` in `sources/web.py` blocks non-HTTP(S) schemes, non-standard ports, credentials in the URL, a denylist of local/internal hostnames, and any address that is not public once mapped IPv6/NAT64 is unwrapped (an `allow_hosts` override exists only for fixtures); a total fetch deadline; a runtime check (`ALLOWED_ENRICHMENT_TOOLS`) that keeps a state-changing tool out of the enrichment tool set; an injection suite with offline cases plus a live canary tier; the judge treats candidate text as untrusted and runs against a separate eval DB.
- **Phase 3 addition:** the truncated model text logged per step is untrusted; it's capped at 1,000 characters, never put into a prompt unwrapped, and rendered in Streamlit only via `st.code`/`st.text`/dataframe cells, never Markdown or raw HTML.
- **Residual risk:** a model that obeys an injected instruction and cites the injected page as its source passes code-level validation and the number-match check; only a live canary run, the golden comparison, or the Phase 5 verifier catch that. `fetch_page` can still be pushed toward a public attacker host with context in the query string; there are no secrets in context to leak. DNS rebinding between check and connection is an accepted residual risk.

## 7. Cost and observability
- `costs.py` converts API usage (input, output including thinking, cache read/write, server-side search) to USD; caps are enforced in `loop.py`'s `Budget` against the running total.
- Search is billed separately from tokens; `web_searches` is its own `stats` field and `max_uses` is a hard per-run cap. Search is the dominant cost component of a run, at roughly US$0.01 per search.
- `run_log.stats` is the current observability record.
- **Phase 3:** observability moved from one stats blob per run to queryable rows: `run_log_step` (one row per iteration) and `run_log.failure_category` (the fixed taxonomy), both read by the Observability tab. Historical runs appear in cost/failure trends but have no step rows.
- **Phase 4 (planned):** `BatchBudget` (see [4.8](#48-phase-4-eval-budget-planned)) charges enrichment, judge, calibration and injection spend to one object, soft-capped at one response past the limit. The judge runs on the strong model, which is why it's limited to free-text fields.

## 8. Phase 4 eval budget (planned)

A planning estimate, not a measured full run; actual spend depends on model output and which optional evals are enabled.

| Component | Basis | Estimated spend per full eval |
|---|---|---:|
| Enrichment | 30 companies at the per-company average | US$0.41 |
| LLM judge | About 60 short calls (two free-text fields per company) | US$0.15 |
| Calibration | Planning allowance | US$0.05 |
| Live injection tests | About 6 cases at the per-company average | US$0.08 |
| **Total** | | **About US$0.70** |

| Budget item | Amount | Meaning |
|---|---:|---|
| Eval allocation | US$5 | About 7 average-cost evals |
| Per-invocation cap | US$1.50 | Maximum spend for one invocation, not the expected cost |
| Reserve | US$4 | Unallocated |

The per-invocation cap is soft by at most one model response. `--score-only`, `--only`, `--limit` and `--skip-judge` reduce spend; `--strong` as the generator costs roughly five times more.
