# Risks and open questions

Part of the [Sprout architecture docs](README.md). See the [overview](1.%20overview.md), [cross-cutting concerns](4.%20cross-cutting.md) and [decisions](6.%20decisions.md) for the architecture these risks and ambiguities refer back to.

### 1. Risks

See `project-plan.md`'s risk list for the original funding-sparsity and scraping/ToS risks; not repeated here.

| Risk | Severity | Mitigation |
|---|---|---|
| Hallucinated or misattributed funding | High | Code-enforced sources, verifier, fabricated-funding gate at most 3%, pass the company number for disambiguation |
| Candidate pool noise inflates cost | High | Pre-screen on active officer count (D34), cheap and free; pilot a small batch first |
| Cost overrun (see `project-plan.md` risks for the base mitigation) | Medium | No batch-level cap yet; `BatchBudget` (D24) must land with the Phase 4 evals and the Phase 5 orchestrator must use it before running the full candidate set |
| Prompt injection via pages | High | Delimiters, no write tools, validation, existing size/type limits; offline and live-canary injection tests planned for Phase 4 |
| Runaway agent loops | Medium | Iteration and USD caps, per-run `max_uses` and fetch limits, last-iteration wrap-up message |
| Server-side search billing eats the per-company target | Low | `max_uses` is 3, searches are counted in `stats`; search dominates per-run cost but the total stays well under target |
| `pause_turn` or `server_tool_use` blocks mishandled | Medium | Append `response.content` unchanged; scripted-client tests cover pause and search turns |
| Same-name company confusion | High | Pass company number, incorporation date, SIC codes and locality in the user message; `lookup_companies_house` result is the identity anchor |
| Large pages or long loops inflate input cost | Medium | Tool-result character cap, prompt caching of the growing conversation |
| Pilot companies absent from the candidate pool | Low | CLI accepts a company number and creates the row from Companies House directly (`add_company_by_number`) |
| `fetch_page` URL chosen by the model can carry context to an attacker | Low | No secrets in context; `UrlPolicy` planned for Phase 4, but a public attacker host still passes |
| Non-deterministic model output: an occasional run ends `invalid` or `refused` | Medium | Single repair attempt; Phase 5 needs a retry policy (a failed latest attempt is retried; status is derived from `run_log`, D32) |
| Snippet-only claims cannot be audited | Medium | Code caps them at `medium` confidence and requires a note; the Phase 5 verifier is the real check |
| Funding coverage understated for non-USD figures | Low | Null is the safe failure; the note carries the original figure |
| SDK and model drift | Medium | Pin model IDs explicitly; re-verify before swapping |
| Schema change without migrations | Medium | Reset during development; Alembic before the weekly job |
| Unattended weekly spend | Medium | Hard cap, console spend limit, failure notification |
| Small golden set (32 entries; one company is about 3 points) | Medium | Report counts and percentages; record label date and source; dev and holdout split, gates on the full set only |
| Golden labels wrong, stale or circular | High | Drafted from independent sources, all 32 verified by the user, only verified entries scored; a wrong `company_number` would score the wrong company, so the report shows the resolved Companies House name (the `SC428761` label needs checking) |
| Eval gate is flaky at n=32 | Medium | Set each gate one company below the baseline; re-run failing entries before calling a regression |
| Number-match fabrication check gives false flags or misses | Medium | Review every flag and tune before gating; unverifiable reported separately |
| Judge prefers fluent answers or disagrees with the user | Medium | Free text only, judge model differs from generator, reference-first rubric, calibration set |
| Passing the injection suite is read as safety | Medium | Documented residual risk (see [4.6 Security](4.%20cross-cutting.md#6-security)); no write tools; the Phase 5 verifier; live canary tier |
| SSRF policy gaps (encoded IPs, NAT64, rebinding) | Medium | Parametrised policy tests through an injected resolver; rebinding accepted |
| Logged model text carries injected content | Medium | Text blocks only, 1,000-character cap, never prompted unwrapped, rendered without Markdown or HTML |
| Phase 3 findings come from a biased sample (20 shell-style, name-matched candidates, 0 failures) | Medium | Treat the cost, repair-rate and tool-error figures as a floor; re-check on a mixed batch before setting Phase 4 gate values |
| Failure taxonomy too coarse to guide fixes | Low | Start at stop/error-type level; the step text and `run_log.error_message` carry the detail; split `invalid` only if it dominates |
| Schema grows again in Phase 5 | Low | Both schema items (`run_log.company_id`, `company_news`) are already built (D32, D33); nothing is owed to Phase 5. Per-company status is derived, not stored. Unique or indexed columns cannot be added by `init_db`, so dedupe in code |
| Mixed server and custom tool call in one turn gave an API 400 (reproduced with `--max-iterations 2`) | Low | Fixed in `loop.py` (an orphaned `server_tool_use` block is dropped before the next request); a live deterministic `iteration_cap` run is still not retried |
| SQLite single writer under the Phase 5 worker pool; a raw `cp` snapshot of a WAL database can miss the `-wal` file | Medium | Enable WAL and a busy timeout in `get_engine`, short per-company commits, snapshot with `VACUUM INTO` or the backup API |

### 2. Open ambiguities

| # | Phase | Open question | Current position |
|---|---|---|---|
| A1 | 1 / 5 |  Candidate pool size and the rule for selecting which N companies get enriched in one run | Resolved (D34). It's capped by whichever is smaller: how many candidates pass the officer-count pre-screen, or how many that run's budget can afford at the per-company enrichment cost; not yet validated by an actual pilot run |
| A2 | 2 / 7 | Search/fetch tooling differs across phases | Phase 2 resolved (D8): Anthropic's server-side `web_search` (`max_uses` 3) for search, no server-side `web_fetch`; every page read goes through the custom `fetch_page` tool, which wraps `WebFetcher` so robots, SSRF, size and cache protections apply to every page the agent reads. Still open for Phase 7: the enrichment agent there calls an off-the-shelf MCP fetch server instead of `fetch_page` directly, which would bypass those protections unless `WebFetcher` is wrapped behind the MCP interface or the swap is kept behind a flag (see the [Phase 7 page](phases/phase-7-mcp-server.md)) |
| A3 | 2 | `CompanyProfile.stage` and a round's `stage` in `funding_rounds` can disagree | Resolved: `validate_submission` rejects a mismatch against the most recently announced round as a repairable error, same path as other provenance problems (see the [Phase 2 page](phases/phase-2-enrichment.md#stage-two-independent-fields-reconciled-by-one-repair-a3)). Not checked when no round has an `announced` date, or on a later read of already-saved data |
| A4 | 2 / 7 | Keeping `refresh_company` out of the enrichment agent's tool set | Resolved by design (D26, Phase 4 build): `ALLOWED_ENRICHMENT_TOOLS` checked at runtime and in a test. Phase 7 must update the set deliberately if `fetch_page` is replaced |
| A5 | 2 | `Stage` values and funding-field units | Resolved: Series C/D/E/F are distinct values; funding fields are whole millions of USD |
| A6 | 2 | A re-run that nulls a previously valued field leaves both facts, and facts from URLs no longer cited remain | The winning-value rule is implemented as `db.winning_facts` (see the [Phase 2 page](phases/phase-2-enrichment.md#the-winning-value-rule-a6)): valued beats NULL, then most recent `retrieved_at`, then confidence. Not yet called by any reader; must be wired into whatever reads a "current" profile before Phase 6 |
| A7 | 3 | Logging tool inputs (e.g. the fetched URL) per step | Resolved: not logged; Phase 4 adds `stats.sources` (the seen-URL ledger) to the run stats |
| A8 | 3 | Failure taxonomy granularity | Resolved: stays at eight categories; `invalid_output` is not split by sub-reason |
| A9 | 3 | Granularity of a "step" | Resolved: one model response, which can call several tools; tokens and cost are not split per tool |
| A10 | 3 | Phase 3 findings feed the Phase 4 design | Resolved. All six proposed adjustments are addressed: stratification, repair-rate metric and the profiles-submitted floor are in the Phase 4 design; the cost gate (D36) and judge input (D37, `tool_error_text`) are decided; the mixed-tool-call 400 is fixed in `loop.py`. The sample was shell-style candidates, so gate values should still be set from the Phase 4 baseline |
| A11 | 3 / 5 | `run_log` has no company link except inside `stats.company_id` | Resolved (D32): `run_log.company_id` is a real, indexed, nullable column, backfilled from `stats` |
| A12 | 4 | Cost allocation across evals, repeated runs and prompt iteration | Not itemized against the total budget (see [4.8 Phase 4 eval budget](4.%20cross-cutting.md#8-phase-4-eval-budget-planned)) |
| A13 | 4 / 5 | Ordering of evals vs. the multi-agent split | Resolved: evals (Phase 4) now precede the Phase 5 split |
| A14 | 4 | Fabricated-funding definition | Resolved: number-match against the cited page text as the model saw it, within 1 percent (D21) |
| A15 | 4 | Last-round amount rule | Resolved and confirmed (D22) |
| A16 | 4 | Injection-testing acceptance | Resolved and confirmed: two tiers, offline + live canary (D26) |
| A17 | 4 | Golden-set labelling | Resolved: user has verified the entries in `evals/golden.yaml` |
| A18 | 4 | URL policy: allowlist vs. deny-by-rule | Resolved: deny-by-rule in production since the agent must read arbitrary sites (D25); `allow_hosts` is for fixtures only |
| A19 | 4 | Eval spend estimate vs. proposed caps | Resolved: about US$0.73/run estimate, US$1.50 per-run cap, US$5 total allocation, all confirmed |
| A20 | 4 | Golden-set file format | Resolved: YAML, with `pyyaml` added to the `dev` dependency group |
| A21 | 4 | Source-URL "validity" | Resolved: reports both ledger membership (does the URL match a known, trusted source pattern ) (free) and liveness (does the URL actually resolve right now) (opt-in request) |
| A22 | 4 | Judge model and calibration-set size | Resolved: Sonnet judging Haiku, 12 user-confirmed graded triples in `evals/judge_calibration.yaml`; a coarse signal until the set grows |
| A23 | 5 | Per-company status has no home in the current schema | Resolved (D32): derived from `run_log` plus `run_log.company_id`; no `enrichment_state` table |
| A24 | 5 | News has no company link, big-news score or type | Schema resolved (D33): `company_news` with `news_kind` and `summary`, built but unpopulated; who writes it (a Phase 5 matcher over the existing feed, or a later Phase 2 change) is still open |
| A25 | 5 | Classifier "sub-category" has no schema field | Taxonomy stays flat and frozen |
| A26 | 5 | Discovery-agent output has no dedupe key when `company_number` is NULL | Open |
| A27 | 6 | "Funding history" is not supported by the current model | Resolved: the `funding_round` table (Phase 2), one sourced row per round; replaced on each save, so no history across runs |
| A28 | 6 / 8 | Snapshot delivery mechanism for read-only deployments | Undecided |
| A29 | 6 | Dashboard is meant to be read-only but the console can spend API quota | Needs separating or removing before deploy |
| A30 | 6 | The optional Ask box duplicates MCP access | Needs a read-only guarantee and rate limit |
| A31 | 7 | `refresh_company` sync/async, cooldown and payer | Unspecified; the cooldown can read `run_log.company_id` and `started_at` |
| A32 | 5 | Not a real AI startup (shells, consultancies); 12 of the 20 highest-scored candidates enriched to `Other` with 2 to 3 sourced facts | Resolved (D34): pre-screen on active officer count before enrichment; genuine single-officer startups are a known false-reject case |

### 3. Open items by phase
- **Phase 2:** profile review by the user, a console-invoice check of the search price, and the cost-split confirmation (A12).
- **Phase 3:** A7 to A10 are settled as built.
- **Phase 4:** in progress, design finalized; the label files exist, no eval or guardrail code is built yet. Open for the user: confirm the `SC428761` label, run the baseline, set `GATES`, review the first fabricated-funding flags.
- **Before Phase 5:** both schema additions are already built (`run_log.company_id`, `company_news`); still open: WAL and busy timeout; a retry policy; validating `N` against an actual pilot run (A1, D34); concurrency model for the sync client.
- **Before Phase 6:** the winning-value rule (A6) and the shared service layer (D29). **Before Phase 7:** define `refresh_company` (A31).
- **Before Phases 6 and 8:** snapshot delivery (A28); data licensing and robots recheck.
