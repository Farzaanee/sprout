# Risks and open questions

Part of the [Sprout architecture docs](README.md). See the [overview](1.%20overview.md), [cross-cutting concerns](4.%20cross-cutting.md) and [decisions](6.%20decisions.md) for the architecture these risks and ambiguities refer back to.

### 1. Risks

See `project-plan.md`'s risk list for the original funding-sparsity and scraping/ToS risks; not repeated here.

| Risk | Severity | Mitigation |
|---|---|---|
| Hallucinated or misattributed funding | High | Code-enforced sources, verifier, fabricated-funding gate at most 3%, pass the company number for disambiguation |
| Candidate pool noise inflates cost | High | Pre-screen on active officer count (D34), cheap and free; the 12-company pilot validates it, with 5 rejected high-score candidates as a control |
| Cost overrun (see `project-plan.md` risks for the base mitigation) | Medium | `BatchBudget` (D24) caps `run_evals` and opt-in `sprout.enrich --max-total-usd`; the Phase 6 orchestrator always uses it (default US$5.00, planned runs US$1.50 and US$3.50) with a lock, one cap over all four agents (D38) |
| Prompt injection via pages | High | Delimiters, no write tools, validation, existing size/type limits; offline injection tests built; the live-canary tier is built but not yet run |
| Runaway agent loops | Medium | Iteration and USD caps, per-run `max_uses` and fetch limits, last-iteration wrap-up message |
| Server-side search billing eats the per-company target | Low | `max_uses` is 3, searches are counted in `stats`; search dominates per-run cost but the total stays well under target |
| `pause_turn` or `server_tool_use` blocks mishandled | Medium | Append `response.content` unchanged; scripted-client tests cover pause and search turns |
| Same-name company confusion | High | Pass company number, incorporation date, SIC codes and locality in the user message; `lookup_companies_house` result is the identity anchor |
| Large pages or long loops inflate input cost | Medium | Tool-result character cap, prompt caching of the growing conversation |
| Pilot companies absent from the candidate pool | Low | CLI accepts a company number and creates the row from Companies House directly (`add_company_by_number`) |
| `fetch_page` URL chosen by the model can carry context to an attacker | Low | No secrets in context; `UrlPolicy` (Phase 5) blocks non-public targets, but a public attacker host still passes |
| Non-deterministic model output: an occasional run ends `invalid` or `refused` | Medium | Single repair attempt; the Phase 6 retry policy re-runs a failed latest attempt up to 3 times across runs (D39; status derived from `run_log`, D32) |
| Snippet-only claims cannot be audited | Medium | Code caps them at `medium` confidence and requires a note; the Phase 6 verifier is the real check (D40); its eval is report-only rows, not a gate (D41) |
| Funding coverage understated for non-USD figures | Low | Null is the safe failure; the note carries the original figure |
| SDK and model drift | Medium | Pin model IDs explicitly; re-verify before swapping |
| Schema change without migrations | Medium | Reset during development; Alembic before the weekly job |
| Unattended weekly spend | Medium | Hard cap, console spend limit, failure notification |
| Small golden set (32 entries; one company is about 3 points) | Medium | Report counts and percentages; record label date and source; dev and holdout split, gates on the full set only |
| Golden labels wrong, stale or circular | High | Drafted from independent sources, all 32 verified by the user, only verified entries scored; a wrong `company_number` would score the wrong company, so the report shows the resolved Companies House name (caught and fixed once, on BenevolentAI, see [learnings-ph-5.md](../learnings/learnings-ph-5.md)) |
| Eval gate is flaky at n=32 | Medium | Set each gate one company below the baseline; re-run failing entries before calling a regression |
| Number-match fabrication check gives false flags or misses | Medium | Review every flag and tune before gating; unverifiable reported separately |
| Judge prefers fluent answers or disagrees with the user | Medium | Free text only, judge model differs from generator, reference-first rubric, calibration set |
| Passing the injection suite is read as safety | Medium | Documented residual risk (see [4.6 Security](4.%20cross-cutting.md#6-security)); no write tools; the Phase 6 verifier; live canary tier |
| SSRF policy gaps (encoded IPs, NAT64, rebinding) | Medium | Parametrised policy tests through an injected resolver; rebinding accepted |
| Logged model text carries injected content | Medium | Text blocks only, 1,000-character cap, never prompted unwrapped, rendered without Markdown or HTML |
| Phase 4 findings come from a biased sample (20 shell-style, name-matched candidates, 0 failures) | Medium | Treat the cost, repair-rate and tool-error figures as a floor; re-check on a mixed batch before setting Phase 5 gate values |
| Failure taxonomy too coarse to guide fixes | Low | Start at stop/error-type level; the step text and `run_log.error_message` carry the detail; split `invalid` only if it dominates |
| Schema grows again in Phase 6 | Low | Both schema items (`run_log.company_id`, `company_news`) are already built (D32, D33); nothing is owed to Phase 6. Per-company status is derived, not stored. Unique or indexed columns cannot be added by `init_db`, so dedupe in code |
| Mixed server and custom tool call in one turn gave an API 400 (reproduced with `--max-iterations 2`) | Low | Fixed in `loop.py` (an orphaned `server_tool_use` block is dropped before the next request); a live deterministic `iteration_cap` run is still not retried |
| SQLite single writer under the Phase 6 worker pool; a raw `cp` snapshot of a WAL database can miss the `-wal` file; committed `data/eval.db` and the snapshot must be cleanly closed | Medium | WAL and a 30 s busy timeout in `get_engine`, no write transaction across a model call, a `*.db-wal`/`*.db-shm` gitignore entry; snapshot with `VACUUM INTO` or the backup API (D38) |
| Spend overshoots the batch cap under concurrency | Low | Soft by one response per in-flight call (about `concurrency x US$0.02`); atomic `try_slice`; planned caps leave the ceiling headroom (D38) |
| Verify (Sonnet plus 2 searches) dominates cost; the 70 percent claim rate and per-agent means are estimates | Medium | Skipped when there is no claim, caps in [cross-cutting 9](4.%20cross-cutting.md#9-phase-6-agent-caps-and-run-budget), pilot before the full run, lower `max_uses` first |
| Classifier overwrites a correct enrichment category | Medium | Ablation on the same enrichments with a net-gain rule (D41); revert to enrichment's category if it fails; the classification run keeps `previous_category` |
| News false matches (same-name companies) and sparse RSS | Medium | Model confirms each RSS candidate against the one-liner; ledger-checked URLs; hand-checked sample; RSS-only fallback |
| 429 storm at concurrency 4 | Medium | SDK `max_retries=5`, shared pause gate, one re-run, stop after 5 trips (D38); `api_error` never exhausts a company |
| Per-worker rate limiters loosen shared-host politeness | Low | Concurrency capped at 8; Companies House use is about 3 calls per company; documented in D38 |
| Two workers write one cache key and the second `os.replace` fails | Low | Unique temp name in `DiskCache.put`; the tool handler already turns an exception into an error result |

### 2. Open ambiguities

| # | Phase | Open question | Current position |
|---|---|---|---|
| A1 | 2 / 6 |  Candidate pool size and the rule for selecting which N companies get enriched in one run | Resolved (D34, D39): `--limit N` takes the first N pre-screen survivors by `candidate_score`, bounded by `--max-total-usd`. Not yet validated by an actual pilot run; criteria are on the [Phase 6 page](phases/phase-6-multi-agent.md#build-order-and-live-verification) |
| A2 | 3 / 8 | Search/fetch tooling differs across phases | Phase 3 resolved (D8): Anthropic's server-side `web_search` (`max_uses` 3) for search, no server-side `web_fetch`; every page read goes through the custom `fetch_page` tool, which wraps `WebFetcher` so robots, SSRF, size and cache protections apply to every page the agent reads. Still open for Phase 8: the enrichment agent there calls an off-the-shelf MCP fetch server instead of `fetch_page` directly, which would bypass those protections unless `WebFetcher` is wrapped behind the MCP interface or the swap is kept behind a flag (see the [Phase 8 page](phases/phase-8-mcp-server.md)) |
| A3 | 3 | `CompanyProfile.stage` and a round's `stage` in `funding_rounds` can disagree | Resolved: `validate_submission` rejects a mismatch against the most recently announced round as a repairable error, same path as other provenance problems (see the [Phase 3 page](phases/phase-3-enrichment.md#stage-two-independent-fields-reconciled-by-one-repair-a3)). Not checked when no round has an `announced` date, or on a later read of already-saved data |
| A4 | 3 / 8 | Keeping `refresh_company` out of the enrichment agent's tool set | Resolved by design (D26, Phase 5 build): `ALLOWED_ENRICHMENT_TOOLS` checked at runtime and in a test. Phase 6 adds the same fail-closed check per agent (`ALLOWED_CLASSIFY_TOOLS`, `ALLOWED_NEWS_TOOLS`, `ALLOWED_VERIFY_TOOLS`). Phase 8 must update all four sets deliberately if `fetch_page` is replaced |
| A5 | 3 | `Stage` values and funding-field units | Resolved: Series C/D/E/F are distinct values; funding fields are whole millions of USD |
| A6 | 3 | A re-run that nulls a previously valued field leaves both facts, and facts from URLs no longer cited remain | The winning-value rule is implemented as `db.winning_facts` (see the [Phase 3 page](phases/phase-3-enrichment.md#the-winning-value-rule-a6)): valued beats NULL, then most recent `retrieved_at`, then confidence. Not yet called by any reader; must be wired into whatever reads a "current" profile before Phase 7 |
| A7 | 4 | Logging tool inputs (e.g. the fetched URL) per step | Resolved: not logged; `stats.sources` (the seen-URL ledger) is in the run stats (Phase 5) |
| A8 | 4 | Failure taxonomy granularity | Resolved: stays at eight categories; `invalid_output` is not split by sub-reason |
| A9 | 4 | Granularity of a "step" | Resolved: one model response, which can call several tools; tokens and cost are not split per tool |
| A10 | 4 | Phase 4 findings feed the Phase 5 design | Resolved. All six proposed adjustments are addressed: stratification, repair-rate metric and the profiles-submitted floor are in the Phase 5 design; the cost gate (D36) and judge input (D37, `tool_error_text`) are decided; the mixed-tool-call 400 is fixed in `loop.py`. The sample was shell-style candidates, so gate values should still be set from the Phase 5 baseline |
| A11 | 4 / 6 | `run_log` has no company link except inside `stats.company_id` | Resolved (D32): `run_log.company_id` is a real, indexed, nullable column, backfilled from `stats` |
| A12 | 5 | Cost allocation across evals, repeated runs and prompt iteration | Not itemized against the total budget (see [4.8 Phase 5 eval budget](4.%20cross-cutting.md#8-phase-5-eval-budget)) |
| A13 | 5 / 6 | Ordering of evals vs. the multi-agent split | Resolved: evals (Phase 5) now precede the Phase 6 split |
| A14 | 5 | Fabricated-funding definition | Resolved: number-match against the cited page text as the model saw it, within 1 percent (D21) |
| A15 | 5 | Last-round amount rule | Resolved and confirmed (D22) |
| A16 | 5 | Injection-testing acceptance | Resolved and confirmed: two tiers, offline + live canary (D26) |
| A17 | 5 | Golden-set labelling | Resolved: user has verified the entries in `evals/golden.yaml` |
| A18 | 5 | URL policy: allowlist vs. deny-by-rule | Resolved: deny-by-rule in production since the agent must read arbitrary sites (D25); `allow_hosts` is for fixtures only |
| A19 | 5 | Eval spend estimate vs. proposed caps | Resolved: about US$0.73/run estimate, US$1.50 per-run cap, US$5 total allocation, all confirmed |
| A20 | 5 | Golden-set file format | Resolved: YAML, with `pyyaml` added to the `dev` dependency group |
| A21 | 5 | Source-URL "validity" | Resolved: reports both ledger membership (does the URL match a known, trusted source pattern ) (free) and liveness (does the URL actually resolve right now) (opt-in request) |
| A22 | 5 | Judge model and calibration-set size | Resolved: Sonnet judging Haiku, 12 user-confirmed graded triples in `evals/judge_calibration.yaml`; a coarse signal until the set grows |
| A23 | 6 | Per-company status has no home in the current schema | Resolved (D32): derived from `run_log` plus `run_log.company_id`; no `enrichment_state` table |
| A24 | 6 | News has no company link, big-news score or type | Resolved: schema (D33) is built; the Phase 6 news agent writes it (RSS name match plus one search, model-scored) |
| A25 | 6 | Classifier "sub-category" has no schema field | Taxonomy stays flat and frozen |
| A26 | 6 | Discovery-agent output has no dedupe key when `company_number` is NULL | Open. The discovery agent is intentionally deferred (out of scope for Phase 6, not forgotten), so this stays open until it is designed |
| A27 | 7 | "Funding history" is not supported by the current model | Resolved: the `funding_round` table (Phase 3), one sourced row per round; replaced on each save, so no history across runs |
| A28 | 7 / 9 | Snapshot delivery mechanism for read-only deployments | Undecided |
| A29 | 7 | Dashboard is meant to be read-only but the console can spend API quota | Needs separating or removing before deploy |
| A30 | 7 | The optional Ask box duplicates MCP access | Needs a read-only guarantee and rate limit |
| A31 | 8 | `refresh_company` sync/async, cooldown and payer | Unspecified; the cooldown can read `run_log.company_id` and `started_at` |
| A32 | 6 | Not a real AI startup (shells, consultancies); 12 of the 20 highest-scored candidates enriched to `Other` with 2 to 3 sourced facts | Resolved (D34): pre-screen on active officer count before enrichment; genuine single-officer startups are a known false-reject case |
| A33 | 6 | What counts as an independent second source for the verifier | Proposal (D40): tool-returned and fetched, a different host from the claim's source, not in the enrichment ledger. Syndicated copies of one press release can still pass |
| A34 | 6 | News has no golden labels, so D28 cannot be applied to it by metric | Proposal (D41): hand-check 15 to 20 pilot items against the rubric, compare coverage with an RSS-only matcher, fall back to RSS-only if the agent does not help |

### 3. Open items by phase
- **Phase 3:** profile review by the user, a console-invoice check of the search price, and the cost-split confirmation (A12).
- **Phase 4:** A7 to A10 are settled as built.
- **Phase 5:** done. See the [status table](7.%20status.md) and the [Phase 5 page](phases/phase-5-evals-guardrails.md).
- **Phase 6:** designed (D38 to D41), not built. Both schema additions were already built; WAL/busy timeout, the retry policy and the sync-client concurrency model are now specified. Still open: validating the pre-screen and `N` with the pilot (A1, D34), A33, A34, and the discovery agent (A26, deferred).
- **Before Phase 7:** the winning-value rule (A6) and the shared service layer (D29). **Before Phase 8:** define `refresh_company` (A31).
- **Before Phases 7 and 9:** snapshot delivery (A28); data licensing and robots recheck.
